Chapter 01 · GraphQL의 소개 1.1 Naming & Mental Model

왜 이름이 GraphQL인가? 'Graph'와 무슨 관계인가?

GraphQL = Graph Query Language. 데이터베이스 종류가 아니라 비즈니스 도메인 데이터를 바라보는 멘탈 모델이 그래프이기 때문입니다.

❓ 가장 흔한 오해와 진실

Q. "GraphQL을 쓰려면 Neo4j나 Amazon Neptune 같은 Graph DB가 필요한가요?"

👉 전혀 아닙니다! (No Graph DB Required)

  • GraphQL은 특정 DB에 종속되지 않는 API 계층의 쿼리 언어이자 실행 런타임(Execution Runtime)입니다.
  • 백엔드가 PostgreSQL, Oracle, MySQL 같은 RDBMS이든, MongoDB/Redis 같은 NoSQL이든, 심지어 다른 REST/gRPC 마이크로서비스이든 상관없이 그 위에서 동작합니다.
🧠 비즈니스 도메인은 본질적으로 그래프 $G = (V, E)$ 다
  • 정점 (Vertex / Node): 비즈니스 엔티티 (UnderwritingCase, InsuranceProduct, Coverage, ApplicantProfile)
  • 간선 (Edge / Relationship): 엔티티 간의 연관 관계 (targetProduct, hasCoverage, targetApplicant)
  • 인간의 머릿속과 객체지향 메모리 상에서 도메인 데이터는 2차원 표(Table)가 아니라 서로 연결된 객체 그래프(Application Data Graph)입니다.
▲ 보험 언더라이팅 도메인 그래프: 정점(Type)과 간선(Field)을 따라 원하는 깊이만큼 탐색
Chapter 01 · GraphQL의 소개 1.2 Graph Traversal

SQL vs REST vs GraphQL: 데이터를 바라보는 관점과 그래프 탐색

SQL이 테이블(Table)을 다루고 REST가 개별 리소스 URL을 다룬다면, GraphQL은 루트 노드에서 간선(Edge)을 따라가며 부분 그래프(Subgraph Tree)를 추출합니다.

구분 데이터를 바라보는 멘탈 모델 탐색 방식 및 특징
SQL
Structured Query Language		 2차원 테이블(Table)과 행/열(Row/Column) 정규화된 테이블들을 JOIN하여 평탄화된(Flat) 2차원 결과 집합(ResultSet)을 반환함. 백엔드 DB 전용 질의어.
REST
Representational State Transfer		 개별 리소스 URI (Resource Endpoint) 그래프의 각 노드를 독립된 URL(/cases/1, /products/5)로 쪼개어 노출함. 간선(Edge)을 따라가려면 클라이언트가 여러 번 HTTP 호출을 반복해야 함.
GraphQL
Graph Query Language		 정점(Object Type)과 간선(Field)의 그래프 도메인 전체를 하나의 연결된 스키마 그래프로 정의하고, 클라이언트가 루트 노드(Query)에서 원하는 간선(Field)을 따라가며 계층적 트리(Subgraph)를 단 1회 요청으로 추출함.
GraphQL Query (그래프 탐색 명세서) 
query GetUnderwritingSubgraph {
  # 1. Root(Query)에서 특정 심사건 노드로 진입
  underwritingCase(caseId: "UW-CASE-2026-002") {
    caseId          # 2. 노드의 Leaf(Scalar) 속성 선택
    uwStatus
    targetProduct { # 3. targetProduct 간선(Edge)을 따라 상품 노드로 이동
      productName
      hasCoverage { # 4. hasCoverage 간선을 따라 담보 노드 리스트로 이동
        coverageName
      }
    }
    targetApplicant { # 5. targetApplicant 간선을 따라 피보험자 노드로 이동
      applicantName
      age
    }
  }
}
🔍 그래프 탐색(Traversal) 4단계 원리
  1. 진입점(Root Node) 출발: 모든 탐색은 Query 또는 Mutation 루트 정점에서 시작합니다.
  2. 간선(Edge) 이동: 중괄호 { ... }를 여는 것은 그래프의 간선(연관 필드)을 타고 다음 객체 정점으로 이동한다는 뜻입니다.
  3. 단말(Leaf Scalar) 수확: 더 이상 하위 필드가 없는 스칼라(String, Int, ID)에서 탐색이 종료됩니다.
  4. 예측 가능한 결과: 탐색한 경로 그대로 1:1 매칭되는 JSON 트리가 반환됩니다.
Chapter 01 · GraphQL의 소개 1.3 Official Specification

GraphQL 표준(Specification)은 어디에 정의되어 있는가?

GraphQL은 특정 기업의 독점 라이브러리가 아니라, Linux Foundation 산하 GraphQL Foundation이 관리하는 엄격한 오픈 표준 명세입니다.

📜 표준 ①: GraphQL Specification (언어 및 실행 엔진 표준)

공식 URL: https://spec.graphql.org (github.com/graphql/graphql-spec)

  • Query Language 문법: query, mutation, subscription, fragment, 변수($var), 디렉티브 문법 규정
  • Type System & SDL: scalar, type, input, interface, union, enum, directive 정의 규칙
  • Introspection 규격: __schema, __type 등 자기 기술(Self-describing) 메타 필드 표준
  • Validation & Execution: 쿼리 실행 전 정적 검증 알고리즘, Query 병렬 / Mutation 직렬 실행 규칙, Null Bubbling, 응답 최상위 키(data, errors, extensions) 강제
🌐 표준 ②: GraphQL over HTTP Spec & 언어별 구현체

공식 URL: https://graphql.github.io/graphql-over-http/

  • HTTP POST 요청 본문 JSON 규격: {"query": "...", "operationName": "...", "variables": {...}}
  • 표준 미디어 타입(application/json, application/graphql-response+json) 정의
  • 표준 덕분에 가능한 다국어 구현체 생태계:
    • Java / JVM: graphql-java (엔진) → Spring for GraphQL, Netflix DGS
    • JS / TS: graphql-js, Apollo Server, GraphQL Yoga
    • Python / Go / Rust: Strawberry, gqlgen, async-graphql
Chapter 01 · GraphQL의 소개 1.4 Netflix Case Study

Netflix는 왜, 어떻게 GraphQL을 전사 표준으로 채택했는가?

수백 개의 Spring Boot 마이크로서비스를 Federated GraphQL (Unified Supergraph)로 통합하고, 오픈소스 DGS & Spring for GraphQL 생태계를 이끌고 있습니다.

🎬 1. 도입 배경: Falcor에서 Federated GraphQL로
  • Netflix는 초기에 자체 JSON Graph 기술인 Falcor를 사용했으나, 내부 마이크로서비스가 수백~수천 개로 팽창하고 Netflix Studio Engineering(영화 제작·예산·VFX·계약 등 복잡한 엔터프라이즈 도메인)이 커지면서 한계에 봉착했습니다.
  • 도메인 간 데이터를 유연하게 조합하고 글로벌 표준 도구를 활용하기 위해 GraphQL Federation(연합 그래프)으로 전면 전환했습니다.
🍃 2. Netflix DGS와 Spring for GraphQL의 공식 통합 (2024~)
  • Netflix는 Spring Boot 기반 GraphQL 프레임워크인 Netflix DGS(Domain Graph Service)를 오픈소스로 공개해 발전시켰습니다.
  • 이후 Spring 공식 팀이 Spring for GraphQL을 출시했고, 2024년 Netflix DGS 팀과 Spring 팀이 두 프레임워크의 엔진 통합을 발표하여 현재 DGS는 Spring for GraphQL 위에서 동작합니다.
  • 즉, 본 세미나의 Spring for GraphQL은 Netflix의 대규모 운영 노하우가 집약된 표준 기술입니다.
▲ Netflix의 Federated GraphQL 아키텍처: 각 도메인 팀의 Spring Boot 서버가 하나의 Movie 타입을 공동으로 완성

Chapter 02 · GraphQL 특징과 장점 2.1 Single Endpoint & Multiplexing

핵심 특징 ①: Single Endpoint (POST /graphql)

REST가 리소스마다 별도의 URL을 만든다면, GraphQL은 단 하나의 엔드포인트로 모든 도메인 쿼리를 조합(Multiplexing)합니다.

▲ 화면 초기화 시 3개 도메인 데이터가 필요할 때: REST는 3회 호출, GraphQL은 1회 호출로 통합
curl 예제: 단일 요청으로 3개 도메인 루트 쿼리 동시 조회 
curl -X POST http://localhost:8080/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "query": "query InitWorkbench {
      insuranceProducts { productId productName }
      applicantProfiles { applicantId applicantName }
      underwritingRules { ruleId ruleCode }
    }"
  }'
Spring for GraphQL — 각 루트 필드별 독립 @QueryMapping 
@QueryMapping
public List<InsuranceProduct> insuranceProducts(@Argument String category) {
    return productProvider.getAllProducts(category);
}
@QueryMapping
public List<ApplicantProfile> applicantProfiles() {
    return riskProvider.getAllApplicants();
}
@QueryMapping
public List<UnderwritingRule> underwritingRules(@Argument String riskCategory) {
    return uwProvider.getRules(riskCategory, "Query.underwritingRules");
}
Chapter 02 · GraphQL 특징과 장점 2.2 Zero Over-fetching

장점 ①: Over-fetching (불필요한 데이터 과다 수신) 완벽 해결

서버 컨트롤러나 DTO를 수정하지 않고도, 클라이언트가 필요한 필드만 선택(Field Projection)하여 페이로드 크기를 최적화합니다.

💡 왜 Over-fetching이 문제인가?

REST의 GET /api/v1/products는 항상 모든 상품 속성(담보 목록 + 급부 조건 + 설명까지 수십 개 필드)이 담긴 고정 DTO를 반환합니다. 모바일 앱의 드롭다운 메뉴처럼 오직 상품 ID와 상품명 2개만 필요한 화면에서도 전체 JSON을 다 내려받아야 하므로 네트워크 대역폭과 배터리, 역직렬화 CPU가 낭비됩니다.

Case A. 모바일 드롭다운용 쿼리 (2개 필드만 선택 → ~180 Bytes) 
# 요청 (curl)
curl -X POST http://localhost:8080/graphql \
  -H "Content-Type: application/json" \
  -d '{"query": "{ insuranceProducts { productId productName } }"}'

# 응답 JSON: 담보/급부 리졸버가 실행조차 되지 않음!
{
  "data": {
    "insuranceProducts": [
      {
        "productId": "PROD-HLT-001",
        "productName": "무배당 시그니처 100세 종합건강보험"
      },
      {
        "productId": "PROD-SIMP-002",
        "productName": "무배당 3·2·5 원패스 유병자 간편건강보험"
      }
    ]
  }
}
Case B. PC 언더라이팅 분석 화면용 쿼리 (깊은 계층 전체 선택) 
# 요청 (curl) — 동일한 백엔드 코드, Selection Set만 확장!
curl -X POST http://localhost:8080/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "query": "{ insuranceProducts(category: \"HEALTH\") {
      productId productName underwritingTrack baseMonthlyPremium
      hasCoverage {
        coverageCode coverageName maxCoverageAmount sensitiveRiskCategory

Chapter 03 · GraphQL Schema 완벽 가이드 3.1 SDL & Scalars

SDL(Schema Definition Language) 기본 구조와 Scalar 타입

스키마(*.graphqls)는 서버가 제공할 수 있는 데이터 그래프의 헌법(Contract)입니다.

🧱 GraphQL SDL의 5대 핵심 구성요소
  1. type (Object Type): 서버가 반환하는 도메인 엔티티 노드와 필드 정의
  2. input (Input Object Type): Query/Mutation 인자로 전달할 구조체 정의
  3. type Query: 읽기(조회) 전용 루트 진입점
  4. type Mutation: 쓰기(생성/수정/삭제/시뮬레이션) 전용 루트 진입점
  5. directive @...: 타입·필드·쿼리에 부착하는 메타데이터 및 실행 제어자

※ 그 외 열거형(enum), 다형성 인터페이스(interface), 유니온(union), 실시간 스트리밍(type Subscription)을 지원합니다.

Chapter 03 · GraphQL Schema 완벽 가이드 3.2 Nullability & Lists

Nullability(!)와 리스트([...])의 4가지 조합 완벽 정리

GraphQL의 모든 필드는 기본적으로 Nullable이며, 느낌표(!)가 붙은 위치에 따라 리스트 자체와 원소의 Null 허용 여부가 달라집니다.

SDL 표기 리스트 자체 null 가능? 내부 원소 null 가능? 허용되는 유효한 값 예시 거부되는(에러) 값 예시
[String] O (가능) O (가능) null, [], ["A", null] 없음
[String!] O (가능) X (불가) null, [], ["A", "B"] ["A", null] (원소에 null 포함 불가)
[String]! X (불가) O (가능) [], ["A", null] null (리스트 자체가 null일 수 없음)
[String!]! X (불가) X (불가) [], ["A", "B"] null, ["A", null] (실무 최다 사용 표준)
⚠️ Null Bubbling (널 버블링) 현상 주의!

만약 스키마에서 targetApplicant: ApplicantProfile!처럼 Non-Null(!)로 선언했는데, 런타임에 리스크 서비스 장애로 해당 리졸버가 null이나 예외를 반환하면 어떻게 될까요?

GraphQL 엔진은 Non-Null 계약을 어기지 않기 위해 부모 객체(underwritingCase)까지 통째로 null로 만들어버립니다(Null Bubbling)!

✅ 실무 스키마 Nullability 설계 베스트 프랙티스
  • 식별자와 스칼라 필수 속성(caseId: ID!, productName: String!) 및 컬렉션(hasCoverage: [Coverage!]! — 데이터가 없으면 빈 배열 [] 반환)은 과감하게 !를 붙입니다.
  • 반면 외부 마이크로서비스를 호출하는 하위 연관 객체나 권한에 따라 마스킹/차단될 수 있는 민감 필드는 의도적으로 !를 빼서 부분 성공(Partial Success)이 가능하도록 설계합니다.
Chapter 03 · GraphQL Schema 완벽 가이드 3.3 Output Type vs Input Type

type vs input: 왜 GraphQL은 출력과 입력 타입을 엄격히 분리할까?

Java에서는 DTO 하나를 요청/응답에 같이 쓰기도 하지만, GraphQL 스펙은 type을 인자로 쓰는 것을 문법적으로 금지합니다.

1. type (Output Object Type) — 서버가 반환하는 그래프 노드 
"""보험상품 도메인 출력 타입"""
type InsuranceProduct {
  productId: ID!
  productName: String!
  baseMonthlyPremium: Int!

  # 출력 type의 필드는 자체 인자(Argument)와 리졸버를 가질 수 있음!
  hasCoverage(riskCategory: String): [Coverage!]!
}
2. input (Input Object Type) — 클라이언트가 보내는 입력 구조체 
"""언더라이팅 시뮬레이션 요청 입력 전용 타입"""
input UnderwritingSimulationInput {
  productId: ID!
  applicantName: String!
  age: Int!
  gender: String! = "F"        # input 필드는 기본값(Default) 지정 가능!
  occupationName: String!
  occupationGrade: Int! = 1
  isSmoker: Boolean!
  bmi: Float!
  riskFactorCodes: [String!]!  # 순수 스칼라 또는 다른 input만 포함 가능
}
이유 ①: 출력 type은 '동적 계산 필드(인자)'와 '순환 참조'를 포함하기 때문
  • 출력 type의 필드는 hasCoverage(riskCategory: String)처럼 파라미터를 받아 서버에서 계산되는 함수(Resolver)일 수 있으며, Product ↔ Case 양방향 순환 참조를 가질 수 있습니다.
  • 반면 클라이언트가 JSON으로 직렬화해 올려보내는 입력값은 순수한 트리 데이터(Value Object)여야 하므로 input으로 분리됩니다.
이유 ②: 보안(Mass Assignment 방지)과 입출력 생명주기 분리
  • 출력 타입(type UnderwritingCase)에는 서버가 채번하는 caseId나 심사 판정 결과인 decision이 들어 있습니다.
  • 입력 전용인 input UnderwritingSimulationInput을 분리함으로써 클라이언트가 조작해서는 안 되는 서버 생성 필드를 스키마 수준에서 원천 차단합니다.
Chapter 03 · GraphQL Schema 완벽 가이드 3.4 Directives (@)

directive (@) 완벽 정리: 실행 제어와 시맨틱 메타데이터

Java의 @Annotation처럼 쿼리문이나 스키마 정의에 부착하여 조건부 필드 실행이나 메타데이터/권한/온톨로지 매핑을 수행합니다.

1. Executable Directives (클라이언트가 쿼리문에 작성)
  • @include(if: Boolean!): 변수 조건이 true일 때만 해당 필드를 조회함.
  • @skip(if: Boolean!): 변수 조건이 true이면 해당 필드 조회를 건너뜀 (서버의 @SchemaMapping 리졸버 자체가 실행되지 않아 비용 절약!).
실행 디렉티브(@include, @skip) 활용 쿼리 예제 
query GetCaseConditional(
  $caseId: ID!,
  $withRules: Boolean!,
  $skipApplicant: Boolean!
) {
  underwritingCase(caseId: $caseId) {
    caseId
    uwStatus
    # $withRules == true 일 때만 심사 규칙 리졸버 호출
    matchedRules @include(if: $withRules) {
      ruleCode
      ruleName
    }
    # $skipApplicant == true 이면 피보험자 리졸버 생략
    targetApplicant @skip(if: $skipApplicant) {
      applicantName
    }
  }
}
2. Type System Directives (서버가 스키마 SDL에 작성)
  • @deprecated(reason: "..."): 구버전 필드의 지원 중단 예고 및 대체 필드 안내 (표준 내장)
  • Custom Directives: directive @이름(...) on OBJECT | FIELD_DEFINITION으로 도메인 계보(@ontologyClass, @ontologyProperty)나 권한(@hasRole) 정의
스키마 디렉티브(@deprecated, @ontologyProperty) 선언 및 적용 
# 1. 커스텀 디렉티브 선언 (schema.graphql)
directive @ontologyProperty(
  uri: String!
  label: String!
  range: String!
  sourceField: String!
  crossServiceJoin: String
) on FIELD_DEFINITION

# 2. 타입 필드에 적용
type InsuranceProduct {
  productId: ID!
  baseMonthlyPremium: Int! @ontologyProperty(
    uri: "ins:baseMonthlyPremium",
    label: "기본 월보험료(원)",
    range: "xsd:integer",
    sourceField: "base_mm_prem"
  )
  oldPrem: Int @deprecated(reason: "Use baseMonthlyPremium instead")
}
Chapter 03 · GraphQL Schema 완벽 가이드 3.5 Query vs Mutation Execution Order

Query vs Mutation: 문법만 다른 것이 아니다! (병렬 실행 vs 직렬 실행 보장)

GraphQL 공식 스펙(Execution 섹션)은 Query 루트 필드의 병렬 실행과 Mutation 루트 필드의 순차(Serial) 실행을 엄격히 구분합니다.

⚡ type Query — 루트 필드 병렬(Parallel) 실행
  • 목적: 부수 효과(Side-effect)가 없는 순수 데이터 읽기 작업 (REST의 GET)
  • 하나의 query 블록 안에 여러 루트 필드(insuranceProducts, applicantProfiles)를 적으면, 엔진은 응답 속도를 높이기 위해 동시에 병렬로 실행할 수 있습니다.
🔒 type Mutation — 루트 필드 순차(Serial) 실행 강제
  • 목적: 데이터 생성/수정/삭제 및 상태 변경 트랜잭션 (REST의 POST/PUT/DELETE)
  • 하나의 mutation 안에 2개의 변경 작업을 적었을 때 병렬로 돌면 경쟁 상태(Race Condition)가 발생합니다. 따라서 스펙 수준에서 위에서 아래로 1번이 완전히 끝난 뒤 2번을 실행하도록 직렬 실행을 보장합니다!

스키마의 Query, Mutation, 그리고 type의 연관 필드가 Java 코드의 어노테이션과 1:1로 매핑됩니다.

@Controller

    // 1. Query.underwritingCase 매핑
    @QueryMapping
    public UnderwritingCase underwritingCase(@Argument String caseId) {
        return uwProvider.getCaseById(caseId);
    }

    // 2. Mutation.simulateUnderwriting 매핑
    @MutationMapping
    public UnderwritingCase simulateUnderwriting(
            @Argument UnderwritingSimulationInput input) {
        return uwProvider.simulateCase(input);
    }

    // 3. UnderwritingCase.targetProduct 하위 객체 리졸버
    @SchemaMapping(typeName = "UnderwritingCase", field = "targetProduct")
    public InsuranceProduct resolveTargetProduct(UnderwritingCase uwCase) {
        return productProvider.getProductById(
            uwCase.targetProductId(),
            "UnderwritingCase(" + uwCase.caseId() + ").targetProduct"
        );
    }

    // 4. UnderwritingCase.targetApplicant 하위 객체 리졸버
    @SchemaMapping(typeName = "UnderwritingCase", field = "targetApplicant")
    public ApplicantProfile resolveTargetApplicant(UnderwritingCase uwCase) {
        return riskProvider.getApplicantById(
            uwCase.targetApplicantId(),
            "UnderwritingCase(" + uwCase.caseId() + ").targetApplicant"
        );
    }
}
Chapter 03 · GraphQL Schema 완벽 가이드 3.7 Advanced Query Patterns

실전 Query 예제: Variables($var), Aliases(별칭), Fragments(조각 재사용)

쿼리 문자열 하드코딩을 피하는 Variables와, 동일 필드를 다른 인자로 동시에 비교 조회하는 Aliases + Fragments 기법입니다.

예제 1: Variables($id)를 분리한 안전한 파라미터 바인딩 (curl) 
curl -X POST http://localhost:8080/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "operationName": "GetCaseById",
    "query": "query GetCaseById($id: ID!) {
      underwritingCase(caseId: $id) {
        caseId
        applicationDate
        uwStatus
        targetProduct { productId productName }
        decision { decisionOutcome finalMonthlyPremium }
      }
    }",
    "variables": {
      "id": "UW-CASE-2026-002"
    }
  }'
예제 2: Aliases + Fragment로 표준형 vs 간편형 두 상품 비교 조회 
curl -X POST http://localhost:8080/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "query": "query CompareTwoProducts {
      standardProduct: insuranceProduct(productId: \"PROD-HLT-001\") {
        ...ProductSummary
      }
      simplifiedProduct: insuranceProduct(productId: \"PROD-SIMP-002\") {
        ...ProductSummary
      }
    }
    fragment ProductSummary on InsuranceProduct {
      productId
      productName
      underwritingTrack
      baseMonthlyPremium
      maxEntryAge
    }"
  }'

Part 1 Wrap-Up Key Takeaways & Self-Check

Part 1 (Chapter 01 ~ 03) 핵심 요약 & 자습 복습 체크리스트

다음 시간(Part 2: N+1 문제와 Batch, Spring 심화 최적화, Security)으로 넘어가기 전 핵심 개념을 점검해 보세요.

✅ Chapter 01 핵심 요약
  • Graph의 의미: Graph DB가 아니라 비즈니스 도메인 엔티티(Node)와 관계(Edge)의 Application Data Graph를 뜻한다.
  • 표준 명세: Linux Foundation 산하 GraphQL Foundation이 spec.graphql.org와 GraphQL over HTTP 스펙을 관리한다.
  • Netflix 사례: 수백 개 MSA를 Federated GraphQL로 묶었으며, DGS와 Spring for GraphQL이 공식 통합되었다.
✅ Chapter 02 핵심 요약
  • Single Endpoint: 모든 쿼리와 뮤테이션이 POST /graphql 단일 진입점으로 들어간다.
  • Over/Under-fetching 해결: 클라이언트가 Selection Set으로 필요한 필드만 고르고, 서버 @SchemaMapping이 다중 도메인 그래프를 조립해 1회 응답한다.
  • Partial Success: Nullable 필드 장애 시 data와 errors를 함께 내려보내 화면 전체 장애를 막는다.
✅ Chapter 03 핵심 요약
  • [T!]!: 리스트 자체와 원소 모두 Non-Null을 보장하는 가장 안전한 컬렉션 표기법이다.
  • type vs input: 계산 필드/순환 참조를 가진 출력 객체(type)와 순수 입력값 구조체(input)는 엄격히 분리된다.
  • Query vs Mutation: Query 루트 필드는 병렬 실행되고, Mutation 루트 필드는 순차(Serial) 실행이 보장된다.
